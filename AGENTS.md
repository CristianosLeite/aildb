# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## What this is

aildb is a local, file-based vector search engine written in AIL (https://github.com/CristianosLeite/ail), a programming language designed to cost few tokens when an AI writes it. The first application is semantic search over a source repository: given a query embedding, return ranked source locations that an agent can open. An index is one portable file, rebuilt from the sources, and a query runs locally without a server. The model is the convenience of SQLite, with LanceDB as the reference for vector search.

Version 1 is the commands `build`, `search` and `check`, the snapshot file, the way a snapshot is published, and four acceptance checks. It was stated in a file `REQUIREMENTS.md`, the user's text, which the user took out of the repository on 2026-11-21; its last form is in the history, at the commit `ddc2b4d` (`git show ddc2b4d:REQUIREMENTS.md`), and the knowledge base cites it under that name. What it asked for is now in the documents below and in the tests, and what is still to be done, in `docs/TODO.md`; the words of the acceptance checks 1 and 4 are in `docs/BACKLOG.md`. Read those before proposing or writing anything.

How it is built and tested:

- aildb is built by the command `ail` of AIL (its `docs/cli.md`), which reads `ail.pkg`: `ail build` compiles `src/aildb.aiw` to `build/aildb`, and `ail fmt` indents the sources. `make` is `ail build`, for whoever types it; `make AIL=<path of the command>` names a command that is not on `PATH`, such as `../ail/build/ail` of a checkout that ran `make`. The library of AIL is the one of that command: the repository has no clone of AIL and no link `lib`, and `ail.pkg` says which version it needs.
- `make test` is `ail test`, `ail fmt --check` and `ail test` in `example/consumer`. `ail test` builds every `testbin` of `ail.pkg` first (`build/aildb-stops`, `build/chunk`, the chunker of the example with `tests/example_chunk.aiw`, `build/example-check` and the programs of the measurements) and runs each test: `tests/<name>.aiw` with `<name>.out`, an optional `<name>.code`, or `<name>.err`; it is compiled and started at the top of the repository and works in the directory of `AIL_TMP`. `ail test <name>` or `make test T=<name>` runs one. `example/consumer` is a package of its own that uses aildb as a dependency, by its directory, and searches a snapshot through `use "aildb:src/lib/search.aiw"` (`docs/library.md`).
- `bench/` has the programs of the measurements, AIL and built by `ail test` too: `run.aiw` (the harness, `build/bench-run`, with `stat.aiw`), `gen.aiw` (the inputs), `scan.aiw` (the scan read in three ways) and `times.aiw`, which compiles `src/main.aiw` with `bench/hook.aiw` into `build/aildb-times`, the engine that says the times of the parts of a search on stderr. `tests/bench_stat.aiw` and `tests/bench_tools.aiw` are their tests.
- `make bench PY=<python with lancedb>` runs `bench/bench.sh`: the inputs at 10,000 and 100,000 records, the snapshots, the LanceDB tables of `bench/lance_make.py`, the comparison of the answers (`bench/lance_same.py`) and the harness on `aildb` and on `bench/lance_query.py`; the report is `build/bench/report.txt`.
- `make example` builds `build/chunk` and `build/example-check` and runs the example in `build/example/`, on the repository and revision of `example/corpus.pin` (AIL at `a5b4559`), with the queries and their expected lines of `example/queries.tsv`.
- The expected output of a test that prints what the engine wrote is made by running the test once and reading the result against what was reasoned or computed outside (Python for bits of floating point, CRC-32 and UTF-8); say in the commit how it was checked.

Where things are:

- `src/aildb.aiw` compiles `src/main.aiw`, the commands and the only file that prints and exits, with the hooks of `src/hook.aiw`, which do nothing: the stop points and syncs of `build` and the four moments of `search` (`hookmark`). `tests/lib/stops.aiw` compiles the same commands with `tests/lib/hook.aiw` into `build/aildb-stops`, which stops or fails a sync where the file `aildb.hook` of a test asks. Nothing of the test hooks may be in `build/aildb` (`tests/cli_build_publish.aiw` checks it).
- `src/lib/`: `crc.aiw` (CRC-32, eight tables), `fmt.aiw` (a double in decimal and as bits, a JSON string), `text.aiw` (a number, lines and fields, a prefix, a valid string, a path that stays in the repository), `topk.aiw` (the best pairs of score and ordinal in a fixed workspace), `snap.aiw` (a snapshot mapped and validated), `pack.aiw` (the part of a snapshot before its vectors), `meta.aiw` (the metadata of `build`), `norm.aiw` (normalization), `search.aiw` (a search of an open snapshot: the query normalized, the records scored and filtered, the best kept, a result read back; the command `search` calls it, and it is what a program that uses aildb as a package is to call). A file names the files it needs with `use`, so a program names one of them alone. Each has `tests/lib_<name>.aiw` or, for the reader, `tests/snap_open.aiw`.
- `example/consumer/`: a package that uses aildb, with its own `ail.pkg`, `src/main.aiw` and `tests/search.aiw`.
- `tests/lib/`: `cmd.aiw` (start `aildb` and print what it did; `aildb` and `aildb-stops` are found in `build/`), `mk.aiw` (a snapshot written from `docs/format.md` with no code of the engine), `wide.aiw` and `oracle.aiw` (the independent implementation of acceptance check 2).

## Rules

The rules for commits, pull requests and written text are those of the AIL repository (user, 2026-11-21); when its `AGENTS.md` changes one of them, it changes here too.

- All repository text is in English: documentation, code comments, commit messages, test names, tool messages and the knowledge base. This holds even when the conversation is in another language.
- AIL sources have the extension `.aiw` and are indented with one tab for each block; `ail fmt` sets it.
- A commit message is `type: subject` (`feat`, `fix`, `test` or `docs`, no scope, lower case, no full stop) and a prose body wrapped at about 70 columns: the problem, what changed and why, how it was verified. One backlog item or fix is one commit, with its tests and documentation.
- Work goes to `main` through a pull request, as in the AIL repository (user, 2026-11-22): a branch is checked out from `main` and named for what it does, its commits follow the rules above, it is pushed, and a pull request to `main` is opened whose title is in the form of a commit subject and whose description says what the branch changes and how it was verified. Nothing is committed on `main` and nothing is pushed to it. The user merges, with a merge commit that keeps the commits of the branch.
- Commit messages and pull request descriptions carry no trailers or attribution lines: no `Co-Authored-By`, no `Signed-off-by`, no "Generated with" footer. This holds even when the tool in use suggests one.
- A figure in a document is one that a command of this repository printed; say with which command, on which day, on which hardware and against which revision of AIL. Do not edit a figure by hand or carry one over from a run that was not made.
- A requirement is met when a test shows it. What is to be documented (precision, tolerance, the integrity check, storage assumptions) is written where the format is documented, not left in the code.

## AIL

The language, its compiler and its libraries are in the AIL repository; its `AGENTS.md` and `docs/language.md` describe them, and they are read before AIL is written here. A checkout is usually beside this repository (`../ailang` on the user's machine; the published name is `ail`). Nothing of it is copied here. Until 2026-11-22 this repository got it as ail-bench does, a file `ail.pin` with a revision and a script that cloned it; since then it is a package (user, 2026-11-22), built by the command `ail` of an AIL that is installed or checked out, whose version the line `ail` of `ail.pkg` asks for. The packages are the pull requests 17 to 24 of the AIL repository; until they are merged there, the command is the one of their branch.

What AIL gives this project, as of its version 0.1.0 (2026-11-22):

- The compiler reads a source on stdin and writes a static, position-independent x86-64 Linux executable on stdout. A `use "path"` is opened relative to the top of the package the file is in, `use "name:path"` in the package `name`, and a path that starts with `lib/` in the library of AIL; the command `ail` tells the compiler where each package is.
- Raw system calls (`sys`), so `mmap`, `fsync`, `rename`, `flock` and the like need no library; a call the compiler has no name for is a `const` with its number.
- `lib/std/io.aiw` (output, arguments), `lib/std/bytes.aiw` (a buffer of bytes that grows), `lib/std/file.aiw` (whole files, directories), `lib/std/proc.aiw` (child processes, the monotonic clock), `lib/std/vec.aiw`, `queue.aiw`, `heap.aiw` and `map.aiw` (collections of 64-bit values), `lib/std/task.aiw` (tasks on a pool of threads) and `lib/nd/` (arrays of doubles).
- Floating point is computed in IEEE binary64: `fadd`, `fmul` and the others on one double, the statements on two doubles at an address (`padd`, `pmul`, `pmadd`), and `fsum` and `fdot`, whose loops keep the sum in a register.
- binary32, which the snapshot file stores, has three statements, written for this project on 2026-11-21: `f4to8 a as x` (the binary32 in the low 32 bits as a double, exact), `f8to4 a as x` (a double rounded to the nearest binary32, ties to even) and `fdot4 a p q n as x` (the start `a` plus the products of `n` binary32 at `p` with `n` doubles at `q`, each product rounded and then added, in order). They are the commits `d5f236b` and `a5b4559` of the AIL repository, merged into its `main` (`e8acf57`).
- There are no float literals and no formatted output of a double in the library.

A library function here follows the rules of the AIL libraries: every name starts with the prefix of its file, a descriptor is bytes owned by the caller, and an error is returned, not a reason to end the program. Only the entry point of a command prints and exits.
